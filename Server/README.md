# Bumper Tanks Game Service

Run the PostgreSQL-backed local stack from the repository root with `docker compose up --build`. For JSON-backed Development mode, set `ASPNETCORE_ENVIRONMENT=Development` and run `dotnet run --project Server/BumperTanks.Server.csproj`.

Endpoints: `GET /health`, `GET /v1/gameplay/tuning`, `POST /v1/identity/anonymous`, `GET /v1/profiles/{playerId}`, `POST /v1/rewards/daily`, `GET /v1/cosmetics`, `POST /v1/cosmetics/purchase`, `POST /v1/matches/complete`, `POST /v1/telemetry`, `POST /v1/crash-reports`, `GET /v1/leaderboard`, and WebSocket `/v1/realtime`.

Remote gameplay tuning is configured through bounded `GameplayTuning__*` environment variables. The public endpoint uses ETags, and Unity caches valid values for seven days. See [remote gameplay tuning](../docs/remote-gameplay-tuning.md).

Call `POST /v1/identity/anonymous` to create an anonymous player identity. The response contains a server-issued `playerId` and 256-bit `accessToken`; persist both on the client and send `Authorization: Bearer <accessToken>` on profile, daily reward, cosmetic purchase, match completion, and telemetry requests. These endpoints reject missing credentials and reject a request body or route player ID that does not match the token owner. The server persists only SHA-256 token hashes, in a JSON file in Development or the PostgreSQL `identity_tokens` table when PostgreSQL storage is selected. Anonymous credentials cannot be recovered if the client loses its token.

The cosmetic catalog and prices live on the server. Purchases atomically debit Battle Coins, record ownership in the persisted profile, reject duplicates, and reject insufficient balances. The Unity garage reads the catalog and owned items from the service; its cosmetic selection only chooses among owned flags and sounds. Purchases require the bearer token issued by the anonymous identity endpoint, and the server checks that the token owner matches the requested player ID.

## Realtime prototype

Connect to `/v1/realtime` over `ws://` in development or `wss://` behind a TLS reverse proxy. Browser `Origin` headers must match `Cors__AllowedOrigins`; native clients without an Origin header are accepted. Each client sends one newline-terminated JSON object per WebSocket text message. After requesting an anonymous identity, start with `{"type":"join","playerId":"<playerId>","accessToken":"<accessToken>","displayName":"Pilot"}`. The server validates the token and requires the supplied player ID to match its owner before creating a room participant. The server replies with `type: joined`, a `roomId`, server-assigned integer `playerId`, `tickRate: 30`, and the room roster. Rooms hold at most eight players. Two real players start a room immediately; a solo player starts after 2.5 seconds, when the server adds bots to fill available slots. Rooms are process-local and are removed when all real players disconnect.

After joining, clients may send `{"type":"input","tick":1,"movement":{"x":1,"y":0},"aim":{"x":0,"y":1},"fire":false,"ability":false}`. The server bounds input values, rejects stale or implausibly future ticks, limits each connection to 60 input frames per second, and simulates movement before broadcasting `type: snapshot` messages with tick, player positions, velocities, and health. Incoming messages are limited to 4 KiB; display names are limited to 24 safe characters; the service limits active connections to 2,048 and active rooms to 256.

The room authority computes an idempotent reward receipt for each authenticated real participant when a match ends, persists Battle Coins and match count, and sends that player's receipt over the WebSocket. Online totals come from the authoritative room state rather than the client. Reconnects using the same authenticated identity resume the same player slot and authoritative state for a configurable grace period (30 seconds by default). After the grace period, the slot is removed and a later join starts a fresh match. The realtime room and match authority remains process-local; multiple server replicas do not share rooms, and reconnects must reach the instance that owns the room.

The once-daily spin chooses 25, 50, 75, or 100 coins on the server and returns the award with the updated profile. Development can use JSON files. Production defaults to PostgreSQL and fails startup if `ConnectionStrings:GameDatabase` is missing; JSON storage is rejected outside Development. PostgreSQL migrations create profile, hashed identity token, completed match, rewarded challenge, provider-event, telemetry, and crash-report tables. Existing JSON profile, identity, telemetry, and crash-report files are not imported automatically.

In PostgreSQL mode, telemetry and crash reports are shared across service instances; telemetry retains the newest 10,000 events, and crash reports deduplicate per player/fingerprint with a 1,000-record cap and 30-day expiry. Realtime rooms, connected-player tracking, and match simulation remain process-local; PostgreSQL-backed persistence does not make active matches shareable across service replicas. Keep the realtime service to one replica until distributed room ownership is implemented. Request validation accepts the 32-character hexadecimal player and match IDs generated by the Unity client, restricts telemetry to the game event names, and bounds submitted match totals.

Match completion uses HMAC-SHA256 attestation in non-Development environments by default. Configure `Rewards__MatchAttestationSecret` with at least 32 UTF-8 bytes and have the trusted multiplayer authority sign the newline-separated UTF-8 fields `playerId`, `matchId`, `gems`, and `eliminations`; send the lowercase hexadecimal signature in `X-Match-Attestation`. The signature must be generated by trusted server-side code. Never put the secret in the Unity client. `Rewards__RequireMatchAttestation` can explicitly enable or disable this check; unsigned match results are accepted by default only in Development. If production attestation is enabled without a valid secret, match completion returns `503`; absent and invalid signatures return `401` and `403` respectively.

Attestation proves that a trusted signer authorized the submitted values; it does not establish that the match authority computed those values honestly. Production deployment still needs a trusted multiplayer authority integration. Profile, identity, rewards, telemetry, and crash-report transactions are PostgreSQL-backed; realtime room ownership remains node-local.

Development profile data defaults to `data/profiles.json`; override this with `Storage__ProfilePath` when using JSON storage.

## Container deployment

`docker compose up --build` starts the API with PostgreSQL and a named database volume. The compose password default is only for localhost development; set `BUMPER_POSTGRES_PASSWORD` before exposing any service beyond the local machine. Production deployments must provide their managed PostgreSQL connection string, HTTPS reverse proxy, allowed browser origins, match-attestation secret, and configured game endpoint. JSON files are Development-only.
